# PFS 数据分析 Agent：完整独立改造计划

> 制定日期：2026-08-28  
> 目标：保留并重新验证 Data-Analysis-Agent 的全部功能，同时完成 PFS 的独立产品身份、用户界面、内部标识、文档、安装和发布体系。  
> 当前基线：第一条 CSV/XLSX + PFS 口径 + DeepSeek Agent + Docker 单容器链路已跑通；完整功能、全栈集成、长任务恢复、发布和线上验收仍未完成。不要用百分比替代功能矩阵状态。

## 1. 完成目标如何判定

“完全独立改造完成”必须同时满足四个条件：

1. **功能完整**：原项目能力清单中的每一项都有对应的 PFS 实现，并通过重新测试；不能用“代码还在”代替“功能可用”。
2. **产品独立**：用户能看到的名称、图标、页面、文案、帮助、安装器、更新提示和导出文件都属于 PFS。
3. **内部独立**：PFS 自有代码中的旧项目类名、变量前缀、配置名、服务名、包名、存储名和构建名完成迁移；需要兼容旧数据时使用有期限的迁移层。
4. **交付可信**：本地、提交、推送、部署、线上五种状态分别有证据，真实模型、真实数据源、长任务和安装包都经过对应环境验收。

第三方许可证、依法必须保留的版权声明和授权记录不属于“品牌水印”，不能为了表面无痕而删除。PFS 应去除的是旧产品身份和宣传痕迹，不是假装第三方代码不存在。

## 3. Phase 0：建立“一项功能一张验收卡”

### 要做什么

先从现有源码和原项目文档生成唯一的《功能兼容矩阵》，避免后续凭印象判断完成度。矩阵至少覆盖：

- 页面入口和交互；
- API；
- Agent 工具；
- 数据源；
- 14 类分析方法；
- 图表类型；
- Excel、报告、PPT、Dashboard 输出；

- MCP、飞书、Workspace、Jobs、Workflows、Teams、Hooks；
- 登录、桌面端、GPU/远程能力、更新和安装。

每项只能使用以下状态：

- `源码存在`：只找到代码；
- `静态通过`：语法或构建通过；
- `模拟通过`：使用固定样例或替身服务通过；
- `本地真实通过`：真实进程和真实输入通过；
- `集成通过`：所依赖服务一起通过；
- `线上通过`：部署环境真实验收通过；

### 验收标准

- 原功能矩阵中的每一项都有唯一编号、源码位置、PFS 入口、测试样例、状态和最近验证日期。

## 6. Phase 3：打通 PFS 第一条完整分析闭环

### 要做什么

完成一条可连续操作、可重复测试的真实用户流程：

```text
新建会话
→ 上传 CSV/XLSX
→ 查看字段、样例、缺失、重复和时间范围
→ 选择分析表
→ 输入业务问题
→ Agent 获取字段并制定分析步骤
→ 执行受限查询/计算
→ 生成图表和结论
→ 显示口径、数据版本、计算依据、耗时和错误
→ 导出结果
```

### 实现重点

- 扩充 PFS typed contract：数据源、分析请求、计划、工具调用、运行事件、产物、成本、审批和错误。
- 把模型决策与 SQL、统计和图表计算分开；数字由确定性程序计算。
- 前端补齐空状态、上传中、分析中、无数据、失败、取消、预算不足和完成状态。
- 固定至少三套报表样例：正常数据、脏数据、口径冲突数据。

### 验收标准

- CSV 和 XLSX 各有一条浏览器端到端测试。
- 每个关键数字能回到数据快照、指标定义和计算步骤。
- 文件错误、字段缺失、空结果、模型未配置和用户取消都有明确结果。
- 桌面和 390px 手机视口均可完成主流程。

## 8. Phase 5：完成 PFS 的可信分析特色

这是 PFS 区别于原项目的产品核心，不只是兼容迁移。

### 要做什么

- Metric Contract：指标名称、公式、粒度、时间范围、过滤条件、负责人和版本。
- Data Quality：缺失、重复、异常、时间断档、口径差异和覆盖范围。
- Calculation Lineage：数据版本、SQL/计算代码、参数、图表、任务和产物哈希。
- Evidence Ledger：来源、抓取时间、内容哈希、片段和可信等级。
- Claim–Evidence：支持、反驳、置信度、核验理由和人工决定。
- 冲突队列：不一致结论、异常数字和无法验证项明确进入待处理状态。
- 成本与运行记录：模型用量、费用、耗时、错误、重试、恢复和人工修改。

### 验收标准

- 任意关键结论都能在界面中查看“数据从哪来、怎么算、谁确认”。
- 重复登记、重试和恢复不会产生重复副作用。
- 矛盾数据不会被静默合并成一个答案。
- 固定评估集真实产生 Claim 覆盖率、引用准确度、冲突识别率和计算一致性指标。

## 12. 每轮改造的固定工作方式

每次只处理一个可验收切片，并固定采用以下顺序：

1. 回读当前文件、项目状态和已有改动。
2. 在功能矩阵中选定准确范围和测试样例。
3. 先写输入、输出、错误和权限契约。
4. 窄范围修改源码，不覆盖无关内容。
5. 运行单元、固定样例、构建和真实进程检查。
6. 对用户可见改动做桌面与移动端回读；对导出物实际打开检查。
7. 更新功能矩阵与状态文档。
8. 分别报告 local、commit、push、deploy、live。

任何一个阶段失败，都保留真实失败结果和阻塞原因，不通过修改文档把它写成成功。
