## 1. 完成目标如何判定

“完全独立改造完成”必须同时满足四个条件：

1. **功能完整**：原项目能力清单中的每一项都有对应的 PFS 实现，并通过重新测试；不能用“代码还在”代替“功能可用”。
2. **产品独立**：用户能看到的名称、图标、页面、文案、帮助、安装器、更新提示和导出文件都属于 PFS。
3. **内部独立**：PFS 自有代码中的旧项目类名、变量前缀、配置名、服务名、包名、存储名和构建名完成迁移；需要兼容旧数据时使用有期限的迁移层。
4. **交付可信**：本地、提交、推送、部署、线上五种状态分别有证据，真实模型、真实数据源、长任务和安装包都经过对应环境验收。

第三方许可证、依法必须保留的版权声明和授权记录不属于“品牌水印”，不能为了表面无痕而删除。PFS 应去除的是旧产品身份和宣传痕迹，不是假装第三方代码不存在。

## 6. Phase 3：打通 PFS 第一条完整分析闭环

### 要做什么

完成一条可连续操作、可重复测试的真实用户流程：

```text
新建会话
→ 上传 CSV/XLSX
→ 查看字段、样例、缺失、重复和时间范围
→ 选择分析表
→ 输入业务问题
→ Agent 获取字段并制定分析步骤
→ 执行受限查询/计算
→ 生成图表和结论
→ 显示口径、数据版本、计算依据、耗时和错误
→ 导出结果
```

### 实现重点

- 扩充 PFS typed contract：数据源、分析请求、计划、工具调用、运行事件、产物、成本、审批和错误。
- 把模型决策与 SQL、统计和图表计算分开；数字由确定性程序计算。
- 前端补齐空状态、上传中、分析中、无数据、失败、取消、预算不足和完成状态。
- 固定至少三套报表样例：正常数据、脏数据、口径冲突数据。

### 验收标准

- CSV 和 XLSX 各有一条浏览器端到端测试。
- 每个关键数字能回到数据快照、指标定义和计算步骤。
- 文件错误、字段缺失、空结果、模型未配置和用户取消都有明确结果。
- 桌面浏览器可以完成主流程。

## 7. Phase 4：按功能组恢复并验证原项目全部能力

这一阶段不按目录搬运，而是按用户能完成的任务逐组交付。

### 4A. 数据接入与管理

- CSV、Excel、多表、DuckDB/本地分析库；
- MySQL/PostgreSQL 等 SQL 数据库；
- HTTP API、飞书多维表格；
- 多来源合并、数据仓库配置保存/加载；
- 数据预览、字段详情、启用/停用、删除和分析表范围。

每种数据源至少验证：连接成功、凭据错误、权限不足、超时、大文件、断开重连和敏感信息不写日志。

### 4B. 查询、清洗与高级分析

- schema、表详情、只读 SQL、派生分析表；
- 数据概况、缺失处理、缩尾、截尾等清洗；
- A/B 测试、分层、决策树、聚类、逻辑回归、回归、筛选；
- ARIMA、SARIMA、VAR、Prophet、GRU 等时间序列能力；
- 其他注册分析能力逐项加入固定输入和期望结果。

每种分析至少验证：正确样例、边界样例、错误输入、结果可重复和指标说明。

### 4C. 图表与输出

- 对图表目录逐项核对实际数量，修正文档数量差异；
- 图表选择、字段映射、颜色、空数据和大数据量；
- Excel、分析报告、PPT、Dashboard 生成与下载；
- 导出文件中的品牌、作者、元数据、数据口径和图表可读性。

验收不能只检查“文件生成了”，必须打开或渲染产物检查内容。

### 4D. Agent 使用体验

- 多模型配置、连接测试、默认模型和切换；
- 实时输出、停止、提示建议、使用量和错误恢复；
- 会话保存、自动保存、加载、重命名和删除；
- Commands、Skills、Memory、Knowledge；
- 工作区挂载、文件读写、checkpoint 和恢复。

### 4E. 扩展与编排

- MCP 服务管理、连接、工具发现和调用；
- Jobs、Workflows、Workflow Runs、审批、重试、恢复、取消和 fork；
- Teams、受限委派和质量检查；
- Hooks、生命周期清理、飞书机器人；
- 流程图、桌面能力和远程/GPU 能力；商业画布已按范围决策退役，不再作为兼容目标。

### 阶段验收标准

- 兼容矩阵中原功能不再停留于“源码存在”。
- 可离线测试的能力至少达到“模拟通过”；依赖真实外部服务的能力达到“集成通过”。
- 因外部账号、硬件或收费服务暂时无法验证的项目必须标记阻塞原因，不计入完成率。

## 8. Phase 5：完成 PFS 的可信分析特色

这是 PFS 区别于原项目的产品核心，不只是兼容迁移。

### 要做什么

- Metric Contract：指标名称、公式、粒度、时间范围、过滤条件、负责人和版本。
- Data Quality：缺失、重复、异常、时间断档、口径差异和覆盖范围。
- Calculation Lineage：数据版本、SQL/计算代码、参数、图表、任务和产物哈希。
- Evidence Ledger：来源、抓取时间、内容哈希、片段和可信等级。
- Claim–Evidence：支持、反驳、置信度、核验理由和人工决定。
- 冲突队列：不一致结论、异常数字和无法验证项明确进入待处理状态。
- 成本与运行记录：模型用量、费用、耗时、错误、重试、恢复和人工修改。

### 验收标准

- 任意关键结论都能在界面中查看“数据从哪来、怎么算、谁确认”。
- 重复登记、重试和恢复不会产生重复副作用。
- 矛盾数据不会被静默合并成一个答案。
- 固定评估集真实产生 Claim 覆盖率、引用准确度、冲突识别率和计算一致性指标。

## 9. Phase 6：安全、预算和长任务可靠性

### 要做什么

- Agent 最大步骤、最大运行时间、模型用量和费用上限。
- 工具白名单、参数检查、工作区边界和统一错误处理。
- 写入、删除、外发和生产数据操作的人工确认。
- 外部网页、上传文件、MCP 和工具结果的提示注入防护。
- 任务 checkpoint、暂停、继续、取消、重试、重启恢复和幂等。
- 结构化日志、运行追踪、关键指标和故障回放。
- 登录、会话归属、多人隔离、凭据存储和日志脱敏。

### 验收标准

- 越权工具、非法路径、超预算、提示注入和重复提交都有自动测试。
- 服务重启后，选定的长任务可恢复且不会重复写入。
- 关闭审批或策略服务时的行为明确；关键写操作默认拒绝而不是默认放行。
- 真实产生成功率、恢复成功率、成本、P50/P95 延迟和错误分类数据。

## 12. 每轮改造的固定工作方式

每次只处理一个可验收切片，并固定采用以下顺序：

1. 回读当前文件、项目状态和已有改动。
2. 在功能矩阵中选定准确范围和测试样例。
3. 先写输入、输出、错误和权限契约。
4. 窄范围修改源码，不覆盖无关内容。
5. 运行单元、固定样例、构建和真实进程检查。
6. 对用户可见改动做桌面端回读；对导出物实际打开检查。
7. 更新功能矩阵与状态文档。
8. 分别报告 local、commit、push、deploy、live。

任何一个阶段失败，都保留真实失败结果和阻塞原因，不通过修改文档把它写成成功。
